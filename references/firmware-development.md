# STM32 固件开发流程

用于驱动、外设接口、中断、DMA 和采样相关改动。先遵守技能入口的授权与代码边界；涉及 CubeMX 时遵守其 USER CODE 机制，不向手写工程强制引入生成器。使用其他库时按其实际接口检查，不凭空引入 HAL。

## 1. 建立当前资源与调用关系

- 从当前配置文件（若有）、初始化源码和工程目标确认实际配置。只记录任务相关的引脚/AF、外设实例、时钟来源、触发链、DMA 请求或通道、中断入口与优先级。
- 每个外设明确配置者、启动者、数据生产者与消费者。已有资源表可引用并核对，不另外维护一份容易失效的副本。
- 区分配置、初始化和运行期操作：例如 CubeMX 工程的 `MX_*_Init()` 配置外设，业务接口按设计启动/停止、发送/接收或更新输出；其他工程沿用现有初始化入口。驱动内部不得悄悄重配其他模块正在使用的资源。

## 2. 保持单处初始化与清晰模块边界

- HAL 工程复用现有句柄、MSP、IRQ 和回调链；其他库复用各自已有入口。不要重复创建同一资源或从参考工程复制整套初始化。
- 生成代码通过其允许的用户区或扩展机制接入；独立业务文件按当前规范组织并登记到正式构建目标。
- 初始化和应用入口沿用当前工程分工；驱动处理器件访问与协议，算法尽可能接受输入、返回结果，避免直接依赖硬件寄存器，便于主机回放。
- 沿用当前目录和接口。仅当任务确需新增模块时设计窄接口，不因“分层”重构全工程。

## 3. 驱动返回状态与等待路径

- 对返回状态的调用处理 `HAL_OK`、`HAL_ERROR`、`HAL_BUSY`、`HAL_TIMEOUT`；按该 API 实际可能的结果编写分支，不强行给返回 `void` 的 API 加状态判断。
- 上述 HAL 状态只适用于 HAL API；LL、寄存器或其他驱动按各自错误标志、返回值与完成条件处理，不假设接口具有相同语义。
- 成功启动 IT/DMA 只表示请求被接受，传输完成和错误应由该 HAL 版本的回调/状态确认；调用返回成功不等于收到完整数据。
- `HAL_BUSY` 先核对句柄状态、并发调用和事务所有权，不能通过反复 DeInit/Init 或强改句柄状态掩盖冲突。
- 阻塞调用与硬件等待有明确退出条件、有效时基和有界恢复。ISR 或时基无法推进的上下文不能依赖相同 tick 超时退出。
- 超时/失败向上层报告实际结果；输出参数不能被当成有效新数据。错误路径说明是否保留旧值、发布无效状态、丢弃半帧或等待恢复。
- 控制等关键路径避免不可接受的阻塞。是否采用 DMA/IT 依据吞吐与时序需求决定，不为所有短事务强制增加 DMA。

## 4. IRQ 与回调分工

- IRQ/回调只做有界的状态记录、必要数据搬运与事件发布；解析、显示、非必要日志留给主循环/任务。
- 核对 IRQ 是否接入当前库要求的处理入口、DMA 是否关联正确资源，以及回调是否过滤正确外设实例；句柄等检查仅对采用相应机制的库适用。
- 多模块共用 HAL 回调时在已有入口分发，不重复定义同名函数。错误、半传输、完成等事件按实际启用模式处理。
- 不在 ISR 动态分配内存，不以无界重试阻塞控制；跨上下文共享数据的同步遵守可靠性参考。

## 5. DMA 缓冲区交接

为本次修改涉及的每条 DMA 数据通路明确以下信息：

| 项目 | 必须明确的内容 |
|---|---|
| 传输配置 | 方向、模式、宽度、长度单位、地址/对齐、可达内存及触发来源 |
| 所有权 | DMA 正在读写哪个区域，CPU 此刻能读写哪个区域 |
| 生命周期 | 缓冲区在传输期间有效，不使用已经退出作用域的局部数组 |
| 发布条件 | 哪个事件证明哪个范围已经完整，内容/长度/序号/状态如何一致发布 |
| 复用条件 | 何时可以覆盖或重新交给 DMA，消费者慢于生产者时如何处理 |
| 异常路径 | 丢帧、溢出、半帧、超时、重启及恢复后如何重新同步 |

- 发送时，DMA 尚未完成读取的区域不能被 CPU 改写；接收时，DMA 正在写入的区域不能作为稳定完整帧使用。
- 单缓冲在重新接收前完成消费/复制，或使用已设计的双缓冲、环形区等方案。环形缓冲明确读写位置与覆盖判定；双缓冲也必须处理消费者过慢。
- 不把一次就绪标志当成所有权协议。重新启用 DMA 覆盖原缓冲区后，主循环再读取旧帧的做法不合格。
- UART 空闲事件不自动等于协议报文完整，需结合协议长度/分隔/校验设计；不能复制示例中固定的停止/重启顺序，须核对本工程 HAL 版本行为。
- 核对链接位置能被当前 DMA 访问；缓存维护只在当前器件确有相关缓存且配置要求时采用，不能套用其他内核或芯片系列的方案。

## 6. 验证与交付

按 [可靠性与验证](reliability.md) 选择源码、主机、构建和实物验证。驱动异常需要进一步定位时转到 [调试取证流程](debugging.md)，先观测初始化/启动/回调/发布链中断在哪一步，不靠反复改超时或延时碰运气。
